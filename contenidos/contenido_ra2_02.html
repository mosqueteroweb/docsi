Funciones de un sistema operativo

El SO actúa como intermediario entre el hardware y las aplicaciones. Sus funciones esenciales garantizan que varios procesos compitan de forma justa y segura por los recursos.

1. Gestión de procesos

El SO crea, planifica y finaliza procesos (programas en ejecución). El planificador reparte la CPU entr e ellos (FIFO, Round Robin, prioridades). La multitarea da sensación de paralelismo repartiendo el tiempo de CPU.

2. Gestión de memoria

Asigna y libera memoria RAM a los procesos, implementa memoria virtual (swap) para usar disco como RAM ampliada y protege el espacio de cada proceso.

3. Gestión de entrada/salida y archivos

  • Controla drivers y dispositivos periféricos.
  • Ofrece un sistema de archivos jerárquico (directorios).
  • Abstrae el hardware para que las apps no lo gestionen directamente.

4. Seguridad y servicios

Gestiona cuentas, permisos y aislamiento; ofrece APIs y servicios (red, impresión) a las aplicaciones.

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • El SO es un "recepcionista" que media. La app no habla con el disco ni con la red directamente: pide al SO ("syscall") y él gestiona. Eso simplifica a las apps y protege al hardware.
  • Proceso ≠ programa. El programa es el archivo en disco; el proceso es ese programa "vivo" en ejecución, con su memoria y estado. Puedes tener el mismo programa en 3 procesos.
  • Todo recurso se comparte. CPU, RAM y disco son finitos; el SO decide a quién toca y cuándo. Por eso existen las funciones de gestión.

Para profundizar en los contenidos actuales

Planificación (scheduling). FIFO atiende por orden; Round Robin da un turno fijo a cada proceso (justo, típico en sistemas interactivos); por prioridades atiende primero a los críticos. El modo de cambiar de proceso se llama context switch y tiene coste (guardar/restore estado), por eso muchos cambios perjudican.

Memoria virtual y swap. Cada proceso "cree" tener toda la RAM para él (espacio de direcciones virtual); el SO lo mapea a la física real. Si falta RAM, mueve páginas a disco (swap): lento pero evita que todo se caiga. Demasiado swap = "thrashing" (la máquina se pasa el tiempo moviendo memoria).

Aislamiento de procesos. El SO impide que un proceso lea la memoria de otro; si uno falla, los demás siguen. Ese muro (modo usuario vs modo kernel) es la base de la estabilidad.

Sistema de archivos. El SO da nombres y carpetas sobre el disco físico; las apps abren "documento.txt" sin saber en qué sector está. La abstracción es clave: cambiar de disco no obliga a reescribir las apps.

APIs y servicios. El SO ofrece funciones (API) para ventanas, red, impresión. Las apps las usan en lugar de programar lo bajo nivel; eso es lo que hace posible el software variado.

Revisión didáctica

  • Programa ≠ proceso. El programa está en disco; el proceso está en ejecución. Error típico igualarlos.
  • Memoria virtual no es "RAM infinita". Usa disco y es lenta; abusar da thrashing. No confundir con más RAM real.
  • Syscall no es "llamar a una función normal". Es pedir al kernel en modo privilegiado; tiene su coste y su protección.
  • El SO no "acelera" la CPU. La reparte; si hay muchos procesos, cada uno recibe menos tiempo.
  • Multitarea es ilusión de paralelismo en un solo núcleo. En un núcleo, alterna; con varios núcleos, sí hay paralelismo real.

Hilo de aprendizaje sugerido: (1) el SO como mediador (syscall) → (2) gestión de procesos (planificador, context switch) → (3) gestión de memoria (virtual, swap) → (4) E/S y archivos (abstracción) → (5) seguridad y APIs → (6) por qué el aislamiento importa.
