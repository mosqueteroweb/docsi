Planificación de tareas automáticas

La automatización permite ejecutar comandos o scripts en momentos concretos (copias de seguridad nocturnas, limpieza, informes). Cada sistema dispone de un programador de tareas.

1. cron en GNU/Linux

cron ejecuta tareas según una expresión de 5 campos (minuto, hora, día-mes, mes, día-semana). El comando crontab -e edita la tabla del usuario.

# Todos los días a las 02:30 ejecuta la copia
30 2 * * * /home/usuario/backup.sh
# Cada lunes a las 18:00 limpia temporales
0 18 * * 1 rm -rf /tmp/cache/*
# Ver tareas programadas
crontab -l
flowchart TD

2. systemd timers

En distros modernas, systemd sustituye a cron con unidades .timer y .service, más precisas y con registro de estado.

# /etc/systemd/system/backup.timer
[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true
[Install]
WantedBy=timers.target
# Activar
sudo systemctl enable --now backup.timer

3. Programador de tareas de Windows

El Programador de tareas (Task Scheduler) de Windows permite crear tareas gráficas o mediante schtasks.

# Crear tarea que ejecuta un script cada día a las 3:00
schtasks /create /sc daily /st 03:00 /tn "Backup" /tr "C:\backup.bat"

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • Una tarea automática es "un despertador para el ordenador". Le dices "a tal hora, haz esto" y él lo hace sin que estés delante. Clave para tareas repetitivas (copias, limpieza).
  • cron y systemd son "dos relojeros distintos". cron es el viejo y simple (5 campos); systemd timers es el moderno (más control, registro de fallos). Mismo objetivo, distinta herramienta.
  • La tarea necesita "el qué" y "el cuándo". Sin un comando concreto o sin permisos, el programador no hace nada. Por eso se prueba a mano antes de automatizarla.

Para profundizar en los contenidos actuales

cron: la expresión de 5 campos. minuto(0-59) hora(0-23) día-mes(1-31) mes(1-12) día-semana(0-7). 30 2 * * * = a las 02:30 cualquier día. El * significa "cualquiera". Un error de orden deja la tarea sin disparar.

systemd timers vs cron. El timer apunta a un .service (el qué) y define cuándo (OnCalendar). Ventaja: si el equipo estaba apagado, con Persistent=true la ejecuta al encender; y ves si falló con journalctl. cron no lleva ese registro tan claro.

Windows: Task Scheduler y schtasks. La GUI programa tareas (copias, scripts) por disparador (hora, al iniciar, al evento). schtasks /create hace lo mismo por línea de comandos; ideal para desplegar en varios equipos.

Permisos y entorno. Una tarea automática corre con el usuario que la definió; si ese usuario no tiene permiso sobre la carpeta destino, falla. También el PATH puede diferir del tuyo interactivo: conviene usar rutas absolutas en los scripts.

Prueba antes de programar. El error típico es programar un script que nunca se probó a mano; falla en silencio a las 3:00. Regla: ejecútalo tú primero y mira la salida.

Revisión didáctica

  • cron no es "ejecutar ahora". Solo dispara en el momento programado; para probar, ejecuta el comando a mano antes de confiar en él.
  • El orden de los 5 campos importa. minuto, hora, día-mes, mes, día-semana. Un desplazamiento los baraja todos. No es "lo que me salga".
  • systemd timer no es "cron con otra cara". Aporta registro de estado, Persistent y dependencias; es distinto modelo, no mera sintaxis.
  • Un script con rutas relativas falla en cron. El entorno de cron tiene PATH mínimo; usa rutas absolutas o define PATH en el script.
  • Task Scheduler no ve "lo que tú ves". Corre con su propio usuario/permisos; si tu script necesita acceso a una unidad de red, hay que darle credenciales.

Hilo de aprendizaje sugerido: (1) por qué automatizar (copias, limpieza) → (2) cron: 5 campos y su orden → (3) systemd timers (service+timer, Persistent) → (4) Windows Task Scheduler/schtasks → (5) permisos y PATH en tareas → (6) probar a mano antes de programar.
