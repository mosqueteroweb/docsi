Seguridad de las contraseñas

La contraseña es el primer factor de autenticación. Su seguridad depende de dos pilares: la política de complejidad que obliga a crear claves robustas, y el almacenamiento cifrado que impide leerlas aunque alguien robe el archivo de contraseñas.

1. Requisitos de complejidad

  • Longitud mínima (p.ej. 12 caracteres).
  • Mezcla de mayúsculas, minúsculas, dígitos y símbolos.
  • No reutilizar las últimas N contraseñas (historial).
  • No usar datos personales fácilmente deducibles.

2. Almacenamiento: hash y sal (salt)

Las contraseñas NUNCA se guardan en texto plano. El sistema aplica una función de resumen (hash) unidireccional; al iniciar sesión se vuelve a calcular el hash y se compara. Para evitar ataques de tablas rainbow se añade una sal aleatoria por usuario que se concatena antes de hashear.

SistemaArchivoFormato típico
Linux/etc/shadow$algoritmo$sal$hash (p.ej. $6$ para SHA-512)
WindowsSAM + NTDSHash NTLM (sin sal por cuenta)
# Ejemplo de línea en /etc/shadow para el usuario ana
ana:$6$R4nd0mSal$8xK...hashed...:19000:7:90:14:::

3. Caducidad y rotación

Las directivas de caducidad obligan a cambiar la clave periódicamente (véase chage en el contenido 02). Las cuentas con contraseñas antiguas son un riesgo.

4. Gestores de contraseñas

  • Un gestor de contraseñas genera y guarda claves únicas cifradas (p.ej. con una contraseña maestra).
  • Evitan la reutilización y facilitan claves largas y aleatorias.
  • Ejemplos: KeePassXC, Bitwarden, pass (Linux).

5. Buenas prácticas

  • Usar autenticación multifactor (2FA) cuando sea posible.
  • No compartir credenciales entre servicios.
  • Aplicar política de bloqueo tras intentos fallidos.

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • La contraseña es "la llave"; la política, "la norma de la cerradura". Una llave débil (123456) se abre con un golpe; la norma obliga a llaves complejas.
  • Guardar el hash no es "guardar la contraseña". El sistema guarda el resultado de una función irreversible; ni sabe tu clave, solo si la que escribes da el mismo resultado.
  • La sal es "sal que echa el cocinero a cada plato". Un valor aleatorio por usuario para que dos contraseñas iguales den hashes distintos. Sin sal, las tablas rainbow las rompen.

Para profundizar en los contenidos actuales

Hash unidireccional. SHA-512 (en Linux $6$) convierte la clave en una huella fija; no se puede "deshashear". Al iniciar, se recalcula y compara. Por eso el administrador no ve tu contraseña, solo el hash.

Sal (salt) contra tablas rainbow. Sin sal, el atacante precalcula hashes de palabras comunes ("password123") y los compara. Con sal aleatoria por usuario, esa tabla no sirve: cada hash es único aunque la clave se repita.

Complejidad vs longitud. Una clave larga (14+ chars) de frases es más fuerte que una corta con símbolos. La política moderna prioriza longitud y evita reutilización antes que "poner un signo".

Historial y caducidad. El historial impide reusar las últimas N; la caducidad fuerza rotación. En equilibrio: demasiada rotación lleva a escribir la clave en un post-it.

2FA y gestores. El segundo factor (móvil, token) protege aunque filtren el hash; el gestor genera claves únicas por servicio, evitando la reutilización que un ataque de "relleno de credenciales" explota.

Revisión didáctica

  • "El admin puede ver mi contraseña" es falso. Solo guarda el hash; si la olvidas, la restablece, no la lee. El hash no se deshace.
  • Hash no es "cifrado reversible". Cifrar se puede descifrar; hashear no. Confundirlos es un error de seguridad grave.
  • Sin sal, dos usuarios con la misma clave comparten hash. Eso permite ataques de diccionario/precalculados. La sal lo evita.
  • Símbolos obligatorios no es "contraseña fuerte". "P@ssw0rd" cumple la norma y es débil. La longitud y la entropía mandan.
  • 2FA no sustituye una clave mala. Ayuda mucho, pero si la clave es "123456" y el 2FA es SMS, un SIM-swap lo salta. Conviene clave decente + 2FA fuerte.

Hilo de aprendizaje sugerido: (1) la contraseña como primer factor → (2) complejidad (longitud > símbolos) → (3) hash unidireccional y por qué no se "lee" → (4) sal contra rainbow → (5) caducidad/historial en equilibrio → (6) 2FA y gestores como capa extra.
