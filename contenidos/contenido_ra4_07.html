Herramientas de monitorización del sistema

La monitorización permite conocer el estado del equipo, detectar cuellos de botella y diagnosticar incidencias. Se apoya en dos fuentes: los registros o logs (qué ha ocurrido) y los visores de recursos (qué está consumiendo el sistema ahora).

1. Registros y logs

  • syslog: sistema de registro estándar en UNIX; suele guardar en /var/log/ (p.ej. /var/log/syslog, /var/log/auth.log).
  • systemd-journald: registro estructurado accesible con journalctl.
  • Windows: el Visor de sucesos (Event Viewer) organiza los eventos en Registros de Windows (Sistema, Aplicación, Seguridad).
# Linux: ver errores del sistema
journalctl -p err -b        # errores desde el arranque actual
tail -f /var/log/syslog      # seguir el log en vivo
# Windows: abrir visor de sucesos
eventvwr.msc

2. Visores de sucesos / eventos

El Visor de sucesos de Windows clasifica los eventos por nivel (Información, Advertencia, Error, Crítico) y facilita filtros y suscripciones. En Linux, además de journalctl, las herramientas dmesg muestran los mensajes del kernel.

3. Monitor de recursos (CPU, RAM, disco, red)

  • Linux: top, htop, free -h (memoria), df -h (disco), iotop, iftop (red).
  • Windows: Administrador de tareas (Rendimiento), Monitor de recursos (resmon) y Monitor de rendimiento (perfmon).

4. Buenas prácticas

  • Revisar periódicamente los logs de errores y seguridad (auth.log).
  • Configurar alertas cuando un servicio cae o la carga supera umbrales.
  • Guardar logs rotados (logrotate) para no llenar el disco.

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • Monitorizar = "el cuadro de mandos del coche". Te dice si va sobrado de gasolina (disco), si el motor suda (CPU) o si algo ha avisado (log). Sin él, conduces a ciegas.
  • Logs y recursos son "el qué pasó" vs "el qué pasa". Los logs cuentan eventos pasados; los visores de recursos muestran el consumo en este instante. Los dos juntos dan la foto completa.
  • Un evento "Error" no siempre es "fuego". Hay niveles (Info, Advertencia, Error, Crítico); aprender a leer el nivel evita correr por cada aviso.

Para profundizar en los contenidos actuales

Logs en Linux: syslog, journald, dmesg. /var/log/ guarda histórico; journalctl lee el registro estructurado de systemd; dmesg muestra mensajes del kernel (hardware, arranque). journalctl -p err -b filtra errores desde el último arranque.

Windows: Event Viewer. eventvwr.msc organiza en Sistema/Aplicación/Seguridad; cada evento tiene ID y nivel. Es la primera parada para diagnosticar un cuelgue o un fallo de inicio de sesión.

Recursos: qué mirar. top/htop (CPU/procesos), free -h (RAM), df -h (disco libre), iftop (red). En Windows, Administrador de tareas → Rendimiento y resmon dan lo mismo.

Cuellos de botella. Si la RAM está llena, el sistema usa disco como memoria (swap) y se vuelve lento; si el disco está al 100%, todo se atasca. La monitorización dice dónde aprieta.

tail -f y seguimiento en vivo. tail -f /var/log/syslog muestra los nuevos mensajes en tiempo real; ideal para ver qué pasa cuando reproduces un fallo. En Windows se filtra el log en vivo.

Revisión didáctica

  • "Error" en el log no es siempre "avería". Hay niveles; un error de un servicio que luego arranca bien es ruido. Hay que leer contexto, no solo el nivel.
  • df -h no es "el uso de la carpeta". Muestra espacio por sistema de archivos; para ver el tamaño de una carpeta hay que du. Confundirlos da números que no cuadran.
  • free -h y el "buff/cache" engaña. Linux usa RAM libre como caché; "usada al 90%" no significa falta memoria si el caché se libera. Hay que mirar disponible.
  • journalctl no es "tail de un archivo". Lee la base de journald, no un .log plano; si el servicio cayó antes del arranque actual, hace falta quitar -b.
  • Event Viewer no es solo "el visor de errores". Tiene filtros y suscripciones; usarlo a ojo entre miles de eventos es inútil sin filtrar por ID/nivel.

Hilo de aprendizaje sugerido: (1) monitorizar = cuadro de mandos → (2) logs (syslog/journald/Event Viewer) y niveles → (3) recursos (top/free/df vs Admin tareas/resmon) → (4) cuellos de botella (RAM→swap, disco 100%) → (5) tail -f y filtros → (6) errores típicos de lectura.
