Resolución de problemas de conectividad

El diagnóstico de red sigue una metodología: verificar capa física, configuración IP, conectividad local (ping), ruta (tracert) y resolución DNS. Herramientas clave: ping, ipconfig/ifconfig/ip, tracert/traceroute.

1. ping

Envía ICMP Echo Request para comprobar alcance y latencia. 'ping 8.8.8.8' valida conectividad básica.

2. ipconfig / ip

ipconfig (Windows) o ip -br addr (Linux) muestran la IP asignada, máscara y gateway. 'ipconfig /release|/renew' renueva DHCP.

3. tracert / traceroute

Muestra la ruta salto a salto hasta el destino, útil para localizar dónde se pierde el tráfico.

4. Metodología de diagnóstico

1) ¿hay enlace físico? 2) ¿IP correcta? 3) ¿llegó al gateway? 4) ¿resuelve DNS? 5) ¿llega al destino?

Ejemplo resuelto en clase

Caso práctico: Resolver un problema de conectividad.

  1. Haz ping 192.168.1.1: si responde, la red local va.
  2. Haz ping 8.8.8.8: si falla, problema de gateway/DNS.
  3. Haz nslookup google.com: si falla, es resolución DNS.
  4. Sigue la lógica capa por capa: físico → IP → gateway → DNS.

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • Diagnosticar red es "seguir el cable imaginario". Del enchufe al destino, capa por capa. Si falla algo intermedio, nada de lo de después funciona. Por eso se va de lo físico a lo lógico.
  • ping = "¿estás ahí?". Manda un eco ICMP; si responde, hay camino. Si no, el problema está antes (o hay firewall que bloquea ICMP).
  • DNS caído parece "sin internet". Si haces ping a 8.8.8.8 (IP) y va, pero a google.com no, el fallo es de nombres, no de red. Separar síntomas ahorra horas.

Para profundizar en los contenidos actuales

Metodología bottom-up. 1) enlace físico (LED, cable); 2) IP (¿DHCP dio una?); 3) gateway (¿llegó al router?); 4) DNS (¿resuelve nombres?); 5) destino. Saltarse pasos lleva a tocar lo que no falla.

ip vs ipconfig/ifconfig. ip -br addr da resumen; ip route la tabla de rutas (gateway). En Windows, ipconfig /all y ipconfig /release|/renew para renovar DHCP.

tracert/traceroute. Muestra cada salto (router) hasta el destino y su latencia. Un salto con * * * localiza dónde se corta la ruta, aunque el destino final no responda.

nslookup / dig. Para DNS: nslookup google.com dice qué IP devuelve el servidor. Si devuelve "server can't find", el DNS no resuelve; si devuelve IP pero no hay ping, el fallo es de ruta/firewall.

ICMP puede estar bloqueado. Que ping falle no siempre es "sin red": muchos firewalls droppean ICMP. Hay que confirmar con TCP (curl, telnet al puerto) antes de decir "no hay conectividad".

Revisión didáctica

  • "No navego" no es "no hay red". Puede ser DNS, gateway o firewall. El árbol de diagnóstico existe para no disparar a ciegas.
  • ping que falla no prueba pérdida de red. ICMP puede estar bloqueado por firewall aunque TCP funcione. Confirmar con curl o telnet puerto.
  • Ping a IP sí, a nombre no = fallo de DNS. Es la pista más clara; no reinicia el router, cambia los DNS.
  • tracert con * no es "fin del mundo". Algunos routers no responden ICMP pero dejan pasar tráfico; un * aislado no corta. Se mira el patrón, no un salto suelto.
  • Renovar DHCP sin soltar antes puede no coger IP nueva. ipconfig /release primero, luego /renew. Hacer solo renew a veces mantiene la vieja.

Hilo de aprendizaje sugerido: (1) diagnóstico capa por capa (físico→lógico) → (2) ping (ICMP) y sus límites → (3) ip/ipconfig (¿IP? ¿gateway?) → (4) nslookup/dig (¿DNS?) → (5) tracert (¿dónde se corta?) → (6) errores (ICMP bloqueado, confundir DNS con red).
