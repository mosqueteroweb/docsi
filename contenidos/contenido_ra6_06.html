Servidores de aplicaciones

Un servidor de aplicaciones ejecuta programas a las que acceden los clientes por red (web, correo, base de datos, RDS). Centraliza la lógica de negocio y los datos.

1. Tipos

  • Web: Apache, Nginx, IIS sirven HTTP/HTTPS.
  • Base de datos: MySQL, Postgres, SQL Server.
  • RDS (Remote Desktop Services): publica aplicaciones de Windows a escritorios remotos.
  • ERP/CRM: aplicaciones de gestión accesibles por navegador.

2. Despliegue

Se instala el servidor, se configura el puerto y los permisos, y se publica tras el cortafuegos. La alta disponibilidad usa balanceo de carga.

Ampliación de contenido

Para entender lo anterior (puentes conceptuales)

  • El servidor de aplicaciones es "la cocina, no el comedor". El cliente (navegador) pide; el servidor prepara y devuelve el resultado. El cliente no hace el trabajo pesado.
  • Web / BD / RDS = "distintos mostradores". Cada servicio atiende por su protocolo (HTTP, SQL, RDP). El mismo equipo puede tener varios.
  • Publicar tras el cortafuegos = "atender por la ventanilla". Solo lo que se abre al exterior es accesible; el resto queda protegido dentro.

Para profundizar en los contenidos actuales

Tipos de servidor. Web (Apache/Nginx/IIS) sirve páginas por HTTP/HTTPS; BD (MySQL/Postgres/SQL Server) guarda y consulta datos; RDS publica apps de Windows a escritorios remotos por RDP (3389).

Separación web-app-BD. El navegador habla con el servidor web, este con la aplicación, y la app con la base de datos. Cada capa puede ir en su máquina; mejora escalabilidad y seguridad.

Despliegue. Se instala, se elige puerto (80/443 web, 3389 RDP, 3306 MySQL) y se publica tras el firewall abriendo solo lo necesario. Abrir de más expone el servicio.

Alta disponibilidad. Un balanceador reparte la carga entre varios servidores idénticos; si uno cae, los otros siguen. Para servicios críticos, no hay "un solo servidor".

RDS vs escritorio remoto simple. RDS publica aplicaciones (no todo el escritorio) a muchos usuarios desde un servidor; es distinto de conectarse al escritorio de un PC concreto.

Revisión didáctica

  • "No carga la web" no siempre es fallo de la app. Puede ser el firewall (puerto 443 cerrado), DNS mal resuelto o certificado caducado. Antes de tocar código, comprueba red y puertos.
  • Abrir todos los puertos "por si acaso" es un error. Se publica solo lo necesario (80/443, 3389...); abrir de más expone servicios al exterior. Menos puertos abiertos, menos superficie de ataque.
  • Servidor de apps ≠ servidor de ficheros. Uno ejecuta lógica (cocina); otro guarda archivos (armario). Confundirlos lleva a montar la app en el sitio equivocado.
  • RDS no es "conectarme a mi PC". RDS publica apps a muchos usuarios desde un servidor Windows; el escritorio remoto a un PC concreto es otra cosa (y suele ser para uno solo).
  • La BD no tiene por qué estar en el mismo equipo. Separar web, app y BD mejora rendimiento y seguridad; meterlo todo en uno es simple pero frágil. No es "lo normal obligatorio".

Hilo de aprendizaje sugerido: (1) servidor = cocina → (2) tipos (web/BD/RDS) → (3) separación de capas → (4) despliegue y puertos → (5) alta disponibilidad → (6) errores (puertos abiertos, RDS vs remoto).
